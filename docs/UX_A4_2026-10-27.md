# Contrôles A4 — noms maximaux et zoom réel

Contrôle local du 27 octobre 2026, limité à l'écran de résultat et au panneau de reprise privée. Aucun changement du code applicatif ni publication.

## Scénario et méthode

Base PostgreSQL jetable `arena_ux`, schéma `ux_20261027`, API de test sur 8087 et front sur 5180. Aucun appel Supabase. Partie terminée via les clients HTTP existants : premier joueur gagnant au tour 1, second joueur ayant terminé sa recherche au tour 2. Le score est 1–0.

Les limites réellement acceptées par le backend sont utilisées : nom de salon de 60 caractères et deux pseudos de 24 caractères sans espaces. Le code de reprise synthétique est conservé dans un fichier ignoré, jamais imprimé, et reste masqué dans les captures.

Les largeurs sont celles d'une iframe contenant l'application réelle, sans modification de la fenêtre Chrome. À 320, 390 et 900 pixels, la barre verticale occupe 15 pixels : les largeurs utiles mesurées sont respectivement 305, 375 et 885 pixels. Ce contrôle de largeur ne constitue pas une preuve de zoom.

Le concepteur a ensuite réglé le zoom de cet onglet à **200 %**. La fenêtre mesurée passe de 958 pixels CSS / ratio 1 à 479 pixels CSS / ratio 2. L'iframe adaptée à la page mesure alors 463 × 424 pixels CSS. Il s'agit d'un zoom réel confirmé par l'utilisateur, sans contrôle du navigateur entier par l'agent.

## Complément — accueil, salon, reprise, attente et éditeur à 200 %

Le zoom de l'origine locale est resté à 200 % lors de la reprise du contrôle : fenêtre de 479 × 515 pixels CSS, devicePixelRatio 2. Cette fois, l'application est ouverte directement dans l'onglet, sans iframe. Largeur utile et largeur totale de contenu : 471 px sur l'accueil, le salon, la reprise, l'historique et la préparation ; aucun débordement horizontal mesuré.

Parcours exécutés avec Entrée et Tab sur les contrôles natifs :

- Résultat vers historique : focus sur `history-title`, puis actualisation et retour au salon. Après retour depuis le duel, `lobby-title` est actif et entièrement visible (haut à 100 px, bandeau jusqu'à 80 px).
- Changer de pseudo : focus sur `welcome-pseudo`, sans perte de la saisie. Accueil et historique contrôlés en sombre.
- Reprise depuis accueil/salon : focus sur le titre ; retour sur le déclencheur Reprendre une partie. Formulaire contrôlé en clair et sombre, sans code saisi.
- Création d'une partie locale au clavier : arrivée sur `waiting-title`, actualisation sans perte du bouton actif. Attente contrôlée en clair ; un invité synthétique rejoint ensuite via le client HTTP local.
- Éditeur du code secret en clair : quatre placements par Entrée, progression de la case sélectionnée, puis Tab depuis Effacer vers Confirmer mon code. Le bouton focalisé est entièrement au-dessus de la navigation fixe : haut 354,84 px, bas 402,84 px, navigation à 443 px. La confirmation n'est pas envoyée dans ce relevé.

### Défaut A4-01 — titre de reprise focalisé mais masqué

À l'ouverture de Reprendre une partie depuis une page déjà défilée, le titre reçoit le focus mais passe derrière le bandeau fixe. Mesure reproduite : haut du titre 17,5 px, bas 53,5 px, bandeau d'arrivée couvrant les 80 premiers pixels. Le titre est donc entièrement masqué, malgré une destination clavier correcte. Les captures claire et sombre montrent le champ sous le bandeau, sans le titre.

Cause localisée : `RecoveryScreen.svelte` appelait seulement `heading.focus()` à l'insertion ; ce défilement natif ne réservait pas la hauteur du `TopBar` fixe. Le concepteur a approuvé la correction de visibilité, sans changement de destination de focus ni de mise en page. **A4-01 corrigé et contre-vérifié localement.**

Le titre conserve son focus puis utilise `scrollIntoView` avec une marge de défilement CSS de 120 px, réduite à 96 px jusqu'à 600 px de largeur. Ces marges réservent le bandeau d'arrivée de 104/80 px sans modifier les dimensions du contenu.

Contre-vérification à 200 %, clair depuis le salon défilé et sombre depuis l'accueil : titre actif entre 96 et 132 px, sous le bandeau de 80 px. Tab atteint le champ ; Retour retrouve le déclencheur. Aucun débordement horizontal (471 px utiles et de contenu). Sur une iframe desktop de 900 px, le titre actif commence à 124 px, sous le bandeau de 104 px, sans débordement (892 px utiles et de contenu).

Contrôles après correction : 83 tests front réussis, aucun ignoré ; lint réussi ; Svelte Check sans erreur ni avertissement ; build réussi, 176 modules (`index-Bw6gDduX.js`, `index-pd-AsOAG.css`). Le premier contrôle Svelte dans le bac à sable ne chargeait pas la configuration Vite : il a été répété avec le chargement autorisé avant de retenir le résultat. Aucune nouvelle suite backend pour ce défilement local. Aucun déploiement.

## Statut après complément

### Complément clavier — correction, abandon et navigation

Contrôles sur l'application locale à 200 %, thème sombre, fenêtre de 479 × 515 pixels CSS et ratio 2. Aucun changement applicatif dans ce complément.

Correction de la partie terminée : Entrée sur Corriger les derniers indices ouvre la région avec le focus sur `correction-title`. Le titre commence à 242 px, sous le bandeau de 64 px ; largeur utile et de contenu : 471 px. Les compteurs sont actionnables par Entrée. Annuler ferme la correction et rend le focus au déclencheur ; aucun enregistrement envoyé.

**A4-02 corrigé après accord — focus aux bornes des compteurs.** Avant correction : à 3 noirs, ajouter un blanc atteignait le total de 4, désactivait le bouton utilisé et rendait le focus au document. Retirer ce blanc pour atteindre zéro reproduisait la perte : `document.activeElement` devenait BODY. Cause : attribut natif disabled dépendant de la valeur, sur les compteurs de correction ; les compteurs d'indices ordinaires utilisaient le même mécanisme. [Capture du défaut au minimum](screenshots/ux-a4-20261027/correction-limite-focus-perdu-zoom-200-sombre.png).

Après accord du concepteur, les huit boutons des deux séries de compteurs utilisent aria-disabled et gardent leur apparence indisponible existante. La fonction adjust refuse tout changement pendant busy ; les bornes existantes de 0 à 4 et la somme maximale de 4 sont conservées. Aucun changement de calcul ou d'envoi des indices.

Contre-vérifications locales à 200 % : correction portée à 3 noirs/1 blanc puis retirée jusqu'à zéro blanc ; focus conservé sur la commande devenue indisponible, sans attribut disabled natif. Activation forcée de la commande à zéro : valeurs inchangées. Envoi de correction retardé de huit secondes : une tentative de baisse reste sans effet sur 2 noirs/1 blanc pendant busy. Cette correction synthétique est ensuite confirmée, sans accès à une partie réelle.

Indices ordinaires : noir monté à 1 puis retiré à zéro, focus conservé ; blanc monté à 4, focus conservé avec aria-disabled=true. Activation forcée au maximum : valeurs inchangées à 0/4. Tab depuis la commande précédente atteint toujours le bouton indisponible. Rendu contrôlé dans les deux thèmes ; largeur utile et contenu de 471 px sans débordement. Aucun envoi des indices ordinaires pendant ce contrôle.
